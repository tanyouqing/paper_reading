# ReasoningBank：从成败轨迹提炼推理记忆，并用多次尝试改善经验

> [!abstract] 作者到底做了什么？
> 让固定参数的智能体把过去成功和失败的执行过程总结为简短策略，下一题检索后放入系统提示；进一步让同一题产生多条或多轮经历，用成败对照提炼更好的记忆。
> **输入**：当前任务、环境观察、历史任务与对应记忆。**输出**：任务答案/操作结果/代码补丁，以及追加到外部库的新经验。**改变的对象**：外部记忆及后续提示上下文；没有训练基础模型，没有优化多智能体通信图。

## 2. 出发点：记住操作，不一定记住为何这样做

### 2.1 先看一件具体的事

论文附录图15中的真实任务是：**查询用户在该网站第一次购买的日期**。

无记忆智能体进入个人账户，只查看“最近订单”，就回答了一个日期。它错的关键不是不会点击，而是没有意识到“最近订单”不能证明“第一次购买”。有记忆版本进入完整订单历史并翻页，找到了更早的购买记录。

这里值得保存的不是某个按钮当时的元素编号，而是：

> 遇到“最早、全部、最大”等要求时，先判断当前列表是否覆盖完整数据，检查排序和分页，再回答。

下面围绕这个问题解释机制。除明确引用图15的行为外，后续记忆文本、变体任务及轨迹分支均为**教学重写，不是论文日志或原文逐字摘录**。

### 2.2 作者公开论证中的设计逻辑

依据引言、§3和附录E，可以重建出这条逻辑：

1. 长期工作的智能体会连续遇到不同任务，但通常没有从旧经历中学习的机制，容易重复犯错。
2. 完整轨迹保留很多信息，却又长又含大量页面细节；直接复用容易带来噪声。
3. 把成功轨迹总结成操作流程有所改善，但只知道“怎样走过这条路”，未必知道“什么时候不该走、走完后该验证什么”；失败又常被丢弃。
4. 因而应总结**决策策略、检查条件和防错教训**，并同时利用成功与失败。
5. 单条轨迹仍可能偶然成功或诊断错误；同一任务多次探索能提供差异，让归纳器比较“什么行动有用、什么造成失败”。
6. 不让额外探索只服务当前题的答案，也把其信息沉淀给后续任务。

这是公开材料支持的**设计逻辑重建**，不是作者未公开的私人思维过程。尤其不能将“失败”自动当成某个行动有因果错误的证据：本文依赖LLM解释，并没有对每个行动做受控干预。

## 3. 系统到底有哪两层？

**任务执行层**：读取当前页面/终端结果，结合提示上下文生成动作，在真实基准环境中执行，直到结束。

**经验积累层**：任务完成后，判断大致成败，从轨迹提炼记忆，写入外部库，供下一题检索。

| 部分 | 输入 | 输出 | 谁调用、何时调用 |
| --- | --- | --- | --- |
| 检索器 | 新任务文本、历史任务向量 | 最相近历史任务关联的记忆 | 每个新任务执行前 |
| 执行智能体 | 当前任务、检索记忆、当前观察与动作历史 | 网页动作/Bash命令/最终答复或补丁 | 每次环境交互 |
| 成败判断器 | 任务、轨迹、最终网页状态及答复 | success/failure及判断解释 | 基础记忆流程在任务结束后 |
| 记忆归纳器 | 任务、轨迹及成败方向 | 标题、描述、内容组成的记忆条目 | 判断后，用不同提示处理成败 |
| 外部存储 | 新任务记录、轨迹及其条目 | 增长的JSON/JSONL库及独立向量缓存 | 归纳后追加 |
| MaTTS归纳 | 同一题多条轨迹或多轮检查过程 | 对照后提炼的记忆 | 扩展计算版本使用 |

这些是模块职责，并不等于多个协作agent的运行图。基础模型权重固定；没有梯度下降、RL训练或参数蒸馏。“distill”在此主要指用LLM提炼文本，而非训练学生模型。

## 4. 记忆长什么样？真正检索的是什么？

### 4.1 逻辑存储结构

附录A.2明确说明：一条库记录对应一个历史任务，包含任务、原轨迹和关联记忆；任务向量另存。以下JSON是**逻辑结构教学示意**，不是源码完全相同的序列化格式：

```json
{
  "query": "查找第一次购买的日期",
  "trajectory": ["进入个人账户", "只查看最近订单", "提前回答"],
  "memory_items": [
    {
      "title": "先验证历史记录是否完整",
      "description": "查询最早或全部记录时，应确认列表覆盖范围。",
      "content": "不要将最近记录视为完整历史。检查完整列表入口、排序和分页；覆盖相关记录后再判断最早日期。"
    }
  ]
}
```

**这是一条自然语言策略，不是可直接执行的Python技能。** `content`不提供点击API，也不保存可供解释器运行的分支图。当前页面上的按钮要由执行LLM重新识别和操作。

### 4.2 默认检索不是逐条经验语义匹配

论文附录A.2与公开WebArena实现支持以下流程：

1. 读取新任务描述，例如“找出我最早的一张发票”。
2. 将任务文本编码成向量。
3. 与库中**历史任务描述的向量**计算余弦相似度，默认取最相近的**1个历史任务**。
4. 取出该任务关联的记忆条目，作为系统提示的一部分。
5. 原轨迹虽然被保存，但默认不是把整条旧轨迹一并回放给执行者。

可概括为：

$$
j^*=\arg\max_{j<i}\operatorname{sim}(e(q_i),e(q_j)),\qquad R_i=\operatorname{items}(j^*)
$$

- $q_i$：新任务；$q_j$：已经完成的历史任务。
- $e$：嵌入模型；$\operatorname{sim}$：余弦相似度。
- $R_i$：该历史任务关联的全部记忆条目。

这是对默认方法的解释性写法，不是论文新增的训练目标。实际源码还给新任务检索向量附加了意图匹配指令，见第9节。**top-1经验不等于只取1条记忆**：基础归纳每条轨迹最多可生成3条。

### 4.3 取回来之后，怎样改变执行？

系统提示告诉执行者：这些是过往交互的经验，可以在相关时使用；每步先讨论是否使用，再行动。

在“最早发票”这个教学变体中，执行者可能先判断：旧经验中的“完整历史检查”适用，于是寻找完整发票列表和排序，而不是直接使用首页最近几条记录。

但这只是**LLM在上下文中的相关性判断**。系统没有显式检验“当前页面确实存在同样的分页语义”，也没有一个经过校准的成功概率或可执行契约。向量相近只负责召回，不能证明策略适用。

## 5. 一轮结束后，怎样产生新经验？

### 5.1 不把benchmark真值作为默认学习反馈

基础流程使用与执行者同骨干的LLM判断是否成功。网页判断器可看到任务、行动过程、最终网页状态和最终答复；输出成功/失败（附录图10）。论文设定不让智能体在测试期间读取未来任务或标准答案来学习。

**最终评测**另由benchmark的真实目标/标准协议判成绩。务必分开：

- 学习时的成败判断：可能出错的LLM代理信号。
- 论文表格中的SR：按benchmark评测得到的成绩。

因此成功分支得到的是“被判断为成功的经历”，不是形式验证通过的策略。

### 5.2 同一套格式，两个归纳方向

- 成功：解释为什么这次完成了任务，提炼可迁移的做法。
- 失败：反思为何失败，提炼下次需要避免的陷阱或补充的检查。

两者都限制**最多3条**，每条含`Title / Description / Content`，内容为1–3句话；提示要求避免重复，避免写入特定网站、查询字符串等细节。归纳温度1.0，判断温度0.0（附录A.1–A.2）。

对“只看最近订单”这个教学失败，归纳器可能产生“先检查历史覆盖范围”。它并未执行额外实验来证明此诊断正确，而是根据可见轨迹做解释。

另一个限制：网页观察过长，论文脚注说明用模型在轨迹中的推理文本近似观察信息；公开`induce_memory.py`也抽取`think/action`。因此归纳依据不是逐步完整无损网页状态，更不能将解释当因果真值。

### 5.3 所谓consolidation就是追加

附录A.2明确写了：**直接新增，不做额外剪枝**；合并、遗忘属于未来工作。

因此旧的过宽经验不会被自动原位纠正，新经验与旧经验也可能并存。某个案例展示后期出现更复杂策略，不等于实现了同一条记忆的版本链或显式跨轨迹合并算法。

当前任务的上下文/观察历史可视为执行时的临时状态；论文并未建立一个独立、受控更新的短期—长期分层记忆架构。长期部分就是持续积累的外部库；多agent角色投影、共享协议、经验图边维护均未覆盖。

## 6. MaTTS：多尝试几次，为什么不只是Best-of-N？

测试时扩展计算（test-time scaling）是增加推理阶段的计算。本文额外关心：**这些计算是否改善未来可用的记忆**。

### 6.1 朴素扩展与本文区别

朴素版本可以让同一题运行多次，各条轨迹分别总结并入库。这样更多轨迹只是增加条目，无法利用同题不同结果之间的直接对照。

并行MaTTS的设计是：同一题产生$k$条轨迹，都使用当前旧记忆；然后**把多条轨迹一起交给归纳器**。提示让它比较反复有效的做法与失败中的陷阱，最多产出5条记忆，每条内容1–5句话（图11）。这不是训练对比学习损失，而是LLM读取对照材料后生成文本。

**教学假设例子**：同一订单题产生三条轨迹：

| 轨迹 | 做法 | 可供比较的结果 |
| --- | --- | --- |
| A | 只看最近订单 | 过早回答 |
| B | 不检查状态，反复点击下一页 | 陷入重复浏览 |
| C | 进入完整历史，核对排序和分页进展 | 得到更早记录 |

单独总结C可能只留下“进入完整历史”；联合观察A/B/C则可能总结：“检查历史范围；分页时确认数据变化，重复时更换策略”。这解释了作者希望多轨迹对照提供什么，**没有保证模型一定能提炼出正确且可迁移的原因**。

### 6.2 顺序MaTTS

完成初次轨迹后，提示模型重新检查推理、选中的元素及最终答复；有错就改，正确则确认。后续继续提示“再检查一次”，将中间尝试与纠错信息用于记忆。

它不应被讲成独立新任务验证，也不是每次都从初始环境重新执行。论文定义$k$表示并行轨迹数量或顺序细化规模，并以$k=1$作为不扩展基线；比较这两种$k$不能自动当成总token完全相等。

### 6.3 必须区分三种结果

- **Pass@1**：论文在并行扩展时随机选1条轨迹计分，用于观察单条执行在改进记忆后的表现。它没有消除生成其余轨迹的成本。
- **Best-of-N**：让同骨干LLM读N条轨迹，依据进展、效率、循环、错误等选1条，再评其结果；不是oracle选中正确答案。
- **Pass@k**：N条候选中有没有成功，反映候选覆盖潜力；不代表系统实际能识别正确的那条。

表1使用并行$k=5$的Pass@1；图4的并行结果使用Best-of-N；附录图14另报Pass@k。**53.0、55.1、62.1是不同口径，不能混为一次执行的成绩。**

## 7. Benchmark与评测协议

| 基准 | 任务与输入输出 | 实际在测什么 | 本文规模与配置 |
| --- | --- | --- | --- |
| WebArena | 自托管网站上查信息、导航、改内容；输入用户目标，输出动作及答复/最终网站状态 | 在线交互后的任务成功率SR、平均步数 | 排除Map，684题：Shopping187、Admin182、Gitlab180、Reddit106、Multi29；BrowserGym，每题最多30步 |
| Mind2Web | 给定网页任务的逐步页面表示，预测目标元素与动作 | 离线元素准确率EA、动作F1、步骤成功率SSR、全部步骤正确的任务SR | 1341题：跨任务252、跨网站177、跨领域912；不能直接当真实网站闭环成功率 |
| SWE-Bench-Verified | 给issue及仓库，Bash交互修改代码，提交patch | 官方测试协议下的issue解决率，另报平均步数 | 500题，mini-SWE-Agent式Bash-only循环；主表比较无记忆/Synapse/ReasoningBank |

主模型为Gemini-2.5-Flash、Gemini-2.5-Pro；WebArena另报Claude-3.7-Sonnet。网页执行温度0.7。小模型补充为Gemma-3-12B-Instruct的Shopping实验。SWE未纳入AWM，作者解释其任意Bash动作不易归纳共同固定流程；这是本文选择的基线范围，不能据此推出所有工作流记忆均不适合编程。

基线沿用相同检索、追加机制，主要比较记忆提炼方式（附录B.1）。这有利于观察内容差异，但主表还同时改变了是否利用失败，需要图7消融进一步拆开；也不是对各方法原始最佳工程系统的全栈排名。

测试是顺序积累记忆的在线学习设定：早题可帮助晚题。没有使用未来任务是作者设定；**这不等于“冻结源域记忆后，所有目标题零适配”的严格迁移协议**。跨域成绩需要按该学习过程解释，未看到足够证据为每条经验给出新变体可靠性保证。

## 8. 结果：哪些数字支持了什么？

### 8.1 基础记忆有效，但不等于总计算减少

正式表1，Gemini-2.5-Flash，WebArena整体：

| 方法 | SR（%） | 平均执行步数 |
| --- | ---: | ---: |
| 无记忆 | 40.5 | 9.7 |
| Synapse | 42.1 | 9.2 |
| AWM | 44.1 | 9.0 |
| ReasoningBank | 48.8 | 8.3 |
| ReasoningBank +并行MaTTS，k=5，Pass@1 | 51.8 | 7.9 |

基础ReasoningBank比无记忆高**8.3个百分点**，相对约20.5%；比AWM高4.7个百分点。最后一行的7.9是所报轨迹步数，不能当作每题全部5次尝试及归纳的总成本。

正式表3，SWE-Verified：Flash解决率34.2→38.8，平均步数30.3→27.5；Pro解决率54.0→57.4。这支持收益不限网页任务；没有证明任何仓库、任意分布变化都有效。

正式表2，Mind2Web跨领域Flash：SSR31.9→36.6，**整任务SR1.0→1.6**。既有改善，也显示完整任务仍然困难；不能把36.6误写为任务成功率。

### 8.2 失败内容有独立贡献

图7，Shopping+Flash：

| 提炼方式 | 只用成功轨迹 | 加入失败轨迹 |
| --- | ---: | ---: |
| Synapse | 40.6 | 41.7 |
| AWM | 44.4 | 42.2 |
| ReasoningBank | 46.5 | 49.7 |

这两点比较有解释力：同样只用成功，策略式内容也优于本设置下的工作流内容；加入失败后，不是所有表示都受益。ReasoningBank从失败提炼防错经验，比直接混入失败操作更合适。

它仍没有完全控制条目长度、记忆数量和额外归纳调用的全部成本，因此不宜声称“纯粹抽象程度”是唯一因果来源。

### 8.3 多次探索的收益部分来自记忆对照

Shopping、Flash、并行$k=5$：图4的MaTTS Best-of-5为**55.1**，各轨迹独立归纳的版本为**52.4**。同为扩展计算规模，这为联合对照归纳提供证据；但$k$相同不保证精确token相同。

图5另显示：无扩展ReasoningBank49.7；扩展后随机一条53.0、LLM选最好一条55.1。附录图14的62.1是Pass@5覆盖率，不是可交付成功率。没有用这些数证明“找到了最优策略”。

### 8.4 记忆不是越多越好，判断器也不可靠

- 附录图13：取历史经验数0/1/2/3/4，SR依次39.0/49.7/46.0/45.5/44.4。多取可能引入冲突或无关上下文；这是与解释一致的现象，不是对所有噪声来源的因果分解。
- 图8：Shopping上的判断器与真值一致率**72.7%**。按真值人为翻转标签的实验显示一定抗噪性；真实误判可能系统性关联难题，不能由独立翻转实验完全覆盖。
- 个别策略逐渐复杂的案例是定性观察，不足以证明普遍涌现、单调提升或形式上的RL等价性。
- 主结果未提供足够的多种任务顺序/独立运行置信区间来确认每个小幅差距稳定；未见泄漏证据也不应替作者保证完全排除预训练污染。

### 8.5 完整token账本应怎样读？

附录C.2表5（单任务平均token，原表口径）：

| 方法 | 动作生成 | 判断 | 经验提炼 | 总计 |
| --- | ---: | ---: | ---: | ---: |
| 无记忆 | 50847.4 | — | — | 50847.4 |
| Synapse | 55920.5 | 2594.2 | — | 58514.7 |
| AWM | 53819.6 | 2479.1 | 3074.1 | 59372.8 |
| ReasoningBank | 49306.1 | 2186.3 | 1562.1 | 53054.5 |

ReasoningBank动作生成token略少，但**总计增加约4.34%**。这不是“整体节省token”；更不是并行$k=5$的完整账单。表5没有单列嵌入费用，也不能据其推导输入/输出计价、缓存优惠或硬件延迟。

本文比完全不报模块成本更好，但没有提供普通actor在相同完整硬预算下的充分对照，也未充分分解MaTTS多轨迹、选择、归纳与后续部署摊销。与[[BudgetWeb-2026-Online-Memory-Token-Audit|BudgetWeb]]一起读，才能避免把步数当成本。

## 9. 公开代码核对与复现边界

核对版本：[ed80611788292ea739f1effd31f16c53823b8a0d](https://github.com/google-research/reasoning-bank/tree/ed80611788292ea739f1effd31f16c53823b8a0d)。以下是**当前公开快照的静态行为，不据此否定作者私有实验，也不声称跑过完整复现**。

### 9.1 基础闭环确实能在源码中定位

- [`pipeline_memory.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/pipeline_memory.py)：按数值task_id顺序运行任务→autoeval→归纳；`random.shuffle`被注释。按网站使用独立文件，不能将“Multi”分数当成默认读取所有站点经验库。
- [`run.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/run.py)：读取站点JSONL，调用`select_memory(n=1)`，将命中记录的`memory_items`写入临时提示文本。
- [`memory_management.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/memory_management.py)：历史缓存为查询文本向量；新查询还附意图匹配指令后向量化，与旧缓存归一化点积排序。当前查询缓存追加发生在读取旧缓存后，因此本轮不会靠刚写入的向量匹配自己，但重跑同id需管理旧缓存。
- [`agents/legacy/agent.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/agents/legacy/agent.py)：读取记忆文件并追加到系统消息，没有执行技能程序。
- [`induce_memory.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/induce_memory.py)：提取think/action；读取判断，使用成功/失败提示；将任务、轨迹、状态、生成条目、template_id追加JSONL。`template_id`虽注释去重，这条路径未看到实际按它筛选去重。

**格式差异**：论文逻辑模式是三个字段；公开基础脚本将生成Markdown按空行切成字符串列表，未严格解析成每条`{title,description,content}`对象。不能把教学JSON当真实磁盘文件。它依然使用约定Markdown格式，但没有一个保证内容有效的类型化经验验证器。

### 9.2 多轨迹入口存在实质缺口

[`pipeline_scaling.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/pipeline_scaling.py)和[`induce_scaling.py`](https://github.com/google-research/reasoning-bank/blob/ed80611788292ea739f1effd31f16c53823b8a0d/WebArena/induce_scaling.py)需先修复/核验：

1. 外层创建`results_0...results_{k-1}`，但归纳调用只传循环结束后最后一个`results_i`；归纳器内部`num_samples`循环没有切换目录，重复读取同一`cur_task`。按这条调用链**并不能保证读取k条不同轨迹**。
2. 归纳脚本默认`criteria=gt`，调用者未覆盖；并行流程又未像基础流程那样执行autoeval。默认不能直接称为论文“不依赖真值”的完整实现。
3. `client = CLIENT_DICT[args.model]`拿到类后直接调用实例方法，未实例化；返回值也未按基础流程解包。需要修正调用与序列化后才能执行该路径。
4. 基础脚本的AWM/Synapse失败分支未赋值`generated_memory_item`便进入写入，存在未定义变量路径；重做基线时要明确失败不应怎样写入，并修复。归纳CLI模型选项也未完整覆盖外层模型选择。

以上是可定位的代码问题，不能将它们推断成论文表格造假；但足以说明“代码公开”与“原样一键复现”不同。没有在此仓库替作者修复并偷偷改变评测。

### 9.3 数据、资源与实际难点

- 方法与源码开放（Apache-2.0）；WebArena、Mind2Web、SWE-Verified为公开基准。WebArena需部署网站服务、浏览器、可重复初始状态；Mind2Web是离线网页任务，不能混用协议。
- README包含原始WebArena配置下载、生成配置、`PYTHONPATH`使用vendor harness及SWE安装指引；vendor含购物标注、wishlist评测和操作稳定性修正。复现实验应固定这些版本，不能静默混用不同环境和评测器。
- 主要实验访问云模型及嵌入API；云项目认证、推理费用、模型历史版本可用性均是门槛。Gemma小模型实验并不等于全部结果可离线低成本重现。
- **硬件型号、完整API总账、MaTTS总token/延迟、全部实验墙钟时间：未充分报告，未知。** 不凭模型大小估填。
- 实现难点不是文本总结本身，而是多环境状态隔离、独立轨迹收集、评测与学习反馈隔离、任务顺序/缓存清理、成本完整计数。

## 10. 独特贡献、与已读工作的关系及研究边界

### 10.1 原创贡献应该怎样定位？

它仍属于“总结经验→检索→进入prompt”范式。不能将这个整个闭环当作本文首次提出。

相对本文重点比较的Synapse/AWM，较清楚的新增点是：

1. **记忆内容**从原轨迹/成功操作流程转向成败中的决策原则和防错条件；图7对内容与失败信号分别提供部分支持。
2. **探索与经验的连接**：同题多条轨迹联合对照归纳，而非只做答案选优或独立把每条轨迹入库；同规模消融提供支持。
3. **实证问题**：检验这些文本内容在在线网页、离线跨域操作预测、仓库修复中的作用，并报告判断噪声、检索数量、模块token成本。

这些是内容与系统实验上的贡献，不是新的图结构、优化理论或泛化证明；失败反思本身也非该论文首次发明。作者称“更可迁移”，证据是若干基准平均提升，不能替换为“每条经验在未知任务上已验证”。

### 10.2 与研究设想的对应

| 方向 | 关系 | 边界 |
| --- | --- | --- |
| 经验优化Harness | 直接相关（内容/提示层） | 未搜索Harness源码或优化归纳机制本身 |
| 长期记忆与检索 | 直接相关 | 查询相似度、关联条目、直接追加；无独立成熟短期维护层 |
| 单agent执行 | 直接相关 | ReAct网页/Bash动作循环 |
| 多agent运行图协作 | 未覆盖，可迁移 | 多条轨迹不是角色通信图；未学习路由/拓扑/共享协议 |
| RL强化/参数蒸馏 | 未覆盖 | 无模型参数更新；从失败提炼文字不是策略梯度 |

与[[PolySkill-2026-Polymorphic-Skill-Transfer|PolySkill]]相比，它给的是文字决策建议，没有网站子类/抽象接口/执行方法；与[[NSI-2026-Logic-Grounded-Skill-Induction|NSI]]相比，没有解释器控制流与轨迹一致性检查；与[[MemRL-2026-Utility-Learning-Episodic-Memory|MemRL]]相比，默认没有依据任务反馈学习每条经验的数值效用。

**它留下的一个重要空白**：对同题增加探索可能提高归纳质量，但“经验适用新题吗”“验证它值得再花多少token”并未被显式联合解决。

一个小规模实验（研究建议，不是论文结论）：固定源任务及其记忆，准备同机制的新变体和表面相似但机制不同的任务；比较无记忆、直接top-1、MaTTS记忆、增加适用性检查的记忆。所有生成、判断、检索及验证纳入相同token预算；测SR、负迁移率、总token、检查拒绝率及按真实适用标签衡量的选择准确率。经验冻结后再测目标题，避免目标学习与初始迁移混淆。最先回答的是“对照归纳的收益是否超出同预算直接执行，以及何时应拒用经验”，不是预先假定可靠性检查一定有效。

## 11. 阅读路线与三个问题

**建议次序**：先读图15（最近订单为何会误导）→图1/图2与§3.2（内容及闭环）→附录A.1–A.2（真实格式、top-1与追加）→图3和附录A.3（多轨迹对照及BoN）→图7/图13/表5（失败、数量和成本）→表1–3/附录B（不同benchmark到底测什么）→公开源码及附录D–E（实现和未覆盖范围）。

三个值得进一步验证的问题：

1. 按任务文本相似度召回，与按策略适用条件、环境机制召回相比，什么时候会产生负迁移？
2. 在相同完整token预算下，同题多轨迹对照是否优于把计算用来探索不同任务，或让普通agent多执行几步？
3. 如何区分“失败轨迹中真正导致错误的原因”和“LLM听起来合理的事后解释”，并把验证成本与未来收益一起考虑？
